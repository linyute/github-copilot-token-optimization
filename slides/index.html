快速入門

現在就能做的 14 件事

減少不需要的輸出、降低重複的內容脈絡，然後依任務選擇模型與工具。

最快見效的做法

  1. 僅輸出程式碼的回應：只需要程式碼時，略過說明。
  2. 限制格式：項目符號、一句話、JSON、表格。
  3. 縮小常駐內容脈絡：指示與代理程式檔案。
  4. 預設使用 Auto：只有在有正當理由時才固定使用高階模型。
  5. 簡單問題請使用 Ask 模式。

更多快速見效的做法

  1. 以 applyTo 限定內容脈絡範圍。
  2. 撰寫精確的提示詞：目標檔案、函式、完成條件。
  3. 針對目標模型重新調校提示詞。
  4. 稽核 MCP 伺服器。
  5. 先將富格式檔案轉換為 Markdown。

更多快速見效的做法（續）

  1. 在 Copilot CLI 中執行 /chronicle cost tips & /chronicle improve。
  2. 使用 AI Engineering Coach 檢視 VS Code 的使用習慣。
  3. 對長的 CLI 工具鏈嘗試 CodeAct。
  4. 為重複的程式碼庫導覽建立 Graphify 地圖。

實作 0：建立你的習慣基準線

目標

在學習技巧之前，先找出你最大的 3 個 token 漏洞。

做法：將下列各項標示為綠／黃／紅：輸出冗長度、指示大小、開啟的索引標籤、Agent 的使用、MCP 數量、模型固定、冗長的聊天歷程記錄。

交付成果：個人基準線 + 一項「今天就修正」的行動。

第 1 部分

為什麼 token 很重要

Token 決定了成本、速度、限制與內容脈絡容量。

Token 是子詞

BPE 的行為

  • 常見的單字可以是一個 token。
  • 罕見的單字會被拆成多個片段。
  • 標點符號與贅詞同樣會計入。

核心洞察

Sure, I'd be happy to help! 使用了約 10 個 token，卻沒有回答問題。

成本模型

在供應商的定價範例中，輸出 token 的成本通常明顯高於輸入 token。

輸入比你的提示詞更大

內容脈絡視窗
├─ 系統提示詞
├─ copilot-instructions.md / AGENTS.md
├─ 檔案內容脈絡與開啟的索引標籤
├─ 對話歷程記錄
├─ MCP 工具結構描述
└─ 你輸入的提示詞

一個 20 字的提示詞，可能會連同數千個內容脈絡 token 一起傳送。

Coding Agent 的倍增效應

一次從 issue 到 PR 的執行，並不只是一個請求。

代理程式步驟

規劃、搜尋、讀取檔案、編輯、執行測試、檢查失敗、重試。

累積效應

每個步驟都會重新載入基準內容脈絡，並加上先前的工具結果。

第 2.1 部分

提示詞壓縮

先讓請求清楚，再讓它變短。技術術語與限制條件必須保持精確。

一般的簡潔語言是預設做法。簡寫是選用的。

選用的簡寫

捨棄

沒有增加任何任務資訊的冗詞與客套話。

保留

技術術語、程式碼、檔名、否定、條件與驗收檢查。

[對象] [動作] [原因]。[下一步]。

當片段句會讓人看不出誰做了什麼時，請保留完整的句子。

前後對照

冗長簡潔
你可以幫我審查這個 pull request，並告訴我是否有任何問題嗎？ 審查 PR。標出問題。
你可以解釋這個錯誤訊息的意思，以及我該如何修正嗎？ 說明此錯誤及修正方式。

壓縮層級

層級風格適用時機
簡潔的文字平實、完整的措辭預設
片段句共用術語、簡短子句主詞與條件仍然清楚
高密度簡寫縮寫、箭頭僅在讀者能可靠解讀時

結構化優於散文

POST /api/users
驗證：
- name：字串，必填
- email：字串，必填，格式有效
驗證失敗回傳 400
成功回傳 201，並傳回建立的使用者
儲存至 DB

項目符號與鍵值對能強制讓內容清晰，並減少贅詞。

以程式碼為中心的提示

自然語言

建立一個函式，接收數字、篩選掉負值、將其餘的值加倍，並傳回總和。

以程式碼為中心

fn(nums) -> filter(>0) -> map(*2) -> sum

類似 getUserById，但改用 email。找不到時回傳 404。

將防護欄寫成不變條件

冗長的程序壓縮後的不變條件
請確保每個 SQL 查詢都將值參數化……SQL：僅限參數化查詢。禁止字串串接。
請為任何新的程式碼撰寫測試……新程式碼 -> 測試。涵蓋正常 + 錯誤情況。

第 2.2 部分

語言比較

比較 token 數量，而不是字元數量。

CJK 的假設不成立

語言句子Token相對於英文
英文I met a huge dog51.0x
西班牙文Conoci a un perro enorme81.6x
中文中文對應句112.2x
日文日文對應句112.2x
俄文俄文對應句142.8x

原因

  • BPE 分詞器的訓練資料以英文為大宗。
  • 常見的英文單字通常只需一個 token。
  • CJK 文字的字元較少，但每個字元的 token 較多。
  • 非拉丁文字的成本通常更高；音譯可以有所幫助。

實務原則

提示詞與指示請使用精簡的英文。不要為了節省 token 而翻譯成 CJK 語言。

如果你用母語能更清楚地表達需求，那份清晰度可能勝過節省 token 的好處。

實作 4：分詞器的現實檢驗

目標

以實際的 token 計數，推翻或證實對語言的假設。

做法：挑選一個提示詞。翻譯成你最擅長的非英語語言。在分詞器工具中比較 token 計數。

交付成果：團隊的語言指引：何時必須使用英文，何時可以使用母語。

時間：20 分鐘。

第 2.3 部分

內容脈絡管理

控制哪些檔案、指示與歷程記錄會被傳送。

常駐檔案每一輪都要付費

.github/copilot-instructions.md、AGENTS.md、CLAUDE.md 與類似的檔案，可能成為持續存在的內容脈絡。

當兩個檔案都被載入時，重複的規則會使內容脈絡加倍。

先修剪，再壓縮

刪除重複的規則、過時的筆記，以及程式碼中可見的事實。保留專案專屬的陷阱。

可重複使用的回應範本位於實務設定中。判斷某項規則是否相關，並不需要 token 數量的估算。

內容脈絡整潔

  • 關閉與目前任務無關的檔案。
  • 讓檔案保持專注且小巧。
  • 忽略建構輸出、vendor 目錄與產生的檔案。
  • 在 Business/Enterprise 中，對敏感路徑使用內容排除。
  • 主題改變後，開啟全新的對話。

使用限定範圍的指示

---
applyTo: "src/api/**/*.ts"
---
API 慣例：
- 路由放在 src/api/routes/。Handler 保持精簡，邏輯放在 services/。
- 使用 zod 驗證。
- 以 Result<T,E> 回報錯誤，絕不 throw。

只對相符的檔案載入特定路徑的指引。

常駐、條件式與隨需

先正規化富格式檔案

對快取友善的行為

持久性圖譜導覽

企業注意事項：內容排除

客戶端的行動

針對敏感檔案、產生的套件組合、大型資料檔案與受規範的路徑，設定內容排除。

重要：請先將此視為隱私／原則控制，節省 token 只是附帶效果。請在官方文件中確認目前各介面的支援情形。

輸出控制

要求你需要的答案格式。略過不需要的說明。

僅提供程式碼，不需說明。

格式限制

第 2.5 部分

工作流程最佳化

在縮短個別提示詞之前，先選擇額外負擔較低的工作流程。

提交與 PR 的文字很重要

提交

只有在「為什麼」不明顯時才加上內文。

審查

單行、可執行、並標示嚴重性。

Ask、Edit 與 Agent

Auto 模型預設值

Auto 是不錯的基準：受支援的 Auto 集區、感知組織原則，且依文件對符合資格的付費方案 Chat 用量提供折扣。

Auto 並不代表「升級使用每一個高階模型」。請刻意固定使用高階模型。

模型變更時重新調校提示詞

目標模型：GPT-5.5。
指南：<官方提示詞撰寫指南 URL>
檔案：.github/copilot-instructions.md、.github/instructions/*.md
依照指南調整提示詞。保留行為。減少重工。
只顯示差異。

  • 不可逆的操作。
  • 新人上手與教學。
  • 法規／合規用語。

第 2.6 部分

常駐內容脈絡問題

更多的內容脈絡可能讓代理程式表現更差，成本也更高。

研究訊號

發現觀察到的影響
LLM 產生的內容脈絡檔案在 8 種設定中有 5 種造成損害
平均正確性下降約 2%
Token 成本增加 20-23%
推理額外負擔在所引用的設定中增加約 22%

為什麼內容脈絡有害

冗餘

重複代理程式能在程式碼中找到的事實。

注意力

把重要的規則埋在冗長的內容脈絡中。

錨定

把代理程式導向過時的工具。

訊雜比

讓專案專屬的陷阱更難被發現。

只保留地雷

保留刪除
使用 uv 而非 pip這是一個 Python 專案
資料庫移轉必須依序執行我們使用 PostgreSQL
不要重構身分驗證模組；稽核待處理我們使用 JWT 身分驗證
部署需要 VPN主要分支受到保護

錯誤追蹤器模型

從幾乎空白開始。
代理程式在某處出錯 -> 加入一行。
根本原因被修正 -> 刪除那一行。

當根本問題被修正後，就移除該指示。

實作 10：地雷修剪

目標

在不損失正確性的前提下縮減內容脈絡。

做法：將每項指示標示為可自行發現、風格、地雷、過時、重複。除了真正的常駐地雷之外，其餘一律刪除或限定範圍。

交付成果：最多 10 行的指示檔案草稿。

時間：35 分鐘。

第 2.7 部分

MCP 與工具成本

已載入的工具定義即使未被使用，也會增加輸入。

先量測

/context

System/Tools: MCP + 指示 + 系統提示詞
Messages: 對話歷程記錄
Free Space: 剩餘的內容脈絡

檢查已載入的工具。單看已安裝的伺服器數量，無法反映延後載入的定義或快取行為。

每個工具都會消耗 token

元件大約成本
名稱 + 描述20-50 個 token
簡單的參數結構描述30-80 個 token
複雜的參數結構描述100-300 個 token
每個工具總計100-500 個 token

倍增問題

10 個 MCP 伺服器
x 每個 5 個工具
x 每個工具 200 個 token
= 每個步驟 10,000 個 token

15 個代理程式步驟 = 150,000 個結構描述 token

這是假設的完整目錄載入，並非實際量測的計費。延後載入的定義與快取會改變結果。

稽核規則

  • 停用目前不需要的伺服器。
  • 專案專屬的伺服器請使用工作區設定。
  • 優先使用內建工具，而非重複的檔案系統 MCP。
  • 偶爾才需要的功能請使用技能。
  • 在支援時，依命名空間／模式限定大型外掛程式的範圍。

第 4.2 部分

模型選擇與定價

區分 Copilot 文件、UBB 框架與供應商的 token 定價。

三種定價檢視

檢視回答的問題
GitHub Copilot 文件方案可用性、模型存取、Auto 行為、已發布的訊號
UBB 框架計費切換後的 AI 點數預算與治理

Auto：實際意義

  • 從受支援的 Auto 集區中選擇。
  • 受方案與組織原則約束。
  • 在支援時，針對任務最佳化的路由會考量複雜度、健全度與可用性。
  • 對符合資格的付費方案 Chat 用量提供折扣。
  • 不會自動升級到每一個高階模型。

推理強度

強度用於
低大量的簡單聊天／分類
中在支援時，用於一般的程式開發與大量使用工具的工作
高/最大架構、安全性、全新的問題分解

僅在提供此控制項的模型上使用。

反模式

  • 整天固定使用高階模型。
  • 假設 Auto 會繞過模型存取原則。
  • 將供應商的 API 定價等同於 Copilot 計費。
  • 一開始就為整個組織啟用每一個高階模型。
  • 忽略方案／模型的可用性。

日常的模型指引

  1. 對於不確定的日常工作，優先使用 Auto。
  2. 對於微小且範圍明確的工作，使用輕量模型。
  3. 在計畫清楚之後，一般的實作使用中階模型。
  4. 規劃、架構與困難的偵錯使用強大模型。
  5. 變更模型／工具／代理程式路線時，使用全新工作階段。

基準測試的注意事項

  • 使用基準測試來篩選候選模型；以儲存庫任務測試來決定預設值。
  • 執行框架、工具、擷取與推理強度都會影響分數。
  • 請將成果與成本一起比較，而不是只看分數。
  • 標示來源：已驗證、僅供參考、軼事。
