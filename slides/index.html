快速入門

現在就能做的 14 件事

先刪減不需要的輸出、減少重複的上下文，再依任務選擇模型與工具。

最快見效的做法

  1. 只要程式碼的回應：只需要程式碼時，略過說明。
  2. 限制格式：項目符號、一句話、JSON、表格。
  3. 縮減常駐上下文：指示與 Agent 檔案。
  4. 預設使用 Auto：僅在有正當理由時才固定使用高階模型。
  5. 簡單問題使用 Ask 模式。

更多速效做法

  1. 以 applyTo 限定上下文範圍。
  2. 撰寫精確的提示：目標檔案、函式、完成條件。
  3. 模型行為改變時，重新調校提示。
  4. 稽核 MCP 伺服器。
  5. 先將豐富格式檔案轉換為 Markdown。

更多速效做法（續）

  1. 在 Copilot CLI 中執行 /chronicle cost tips & /chronicle improve。
  2. 使用 AI Engineering Coach 檢視 VS Code 使用習慣。
  3. 針對冗長的 CLI 工具鏈，試用 CodeAct。
  4. 為了反覆的程式碼庫導覽，建置 Graphify 地圖。

實驗 0：建立你的習慣基準

目標

在學習技巧之前，先找出你最主要的 3 個 Token 漏洞。

做法：將下列項目各標記為綠/黃/紅：輸出冗長程度、已載入的指示、開啟的分頁、Agent 使用情況、已載入的工具、模型固定、冗長的對話歷史。

產出：個人基準 + 一項「今天就修正」的行動。

時間：10 分鐘。

第 1 部分

為什麼 Token 很重要

Token 決定成本、速度、限制與上下文容量。

Token 是子詞

BPE 行為

  • 常見的字詞可能只佔一個 Token。
  • 罕見的字詞會被拆成片段。
  • 標點符號與贅詞同樣會計入。

核心洞見

當然，我很樂意幫忙！在沒有回答問題的情況下就用掉約 10 個 Token。

成本模型

在供應商的定價範例中，輸出 Token 的成本通常明顯高於輸入 Token。

輸入遠比你的提示更大

上下文視窗
├─ 系統提示
├─ copilot-instructions.md / AGENTS.md
├─ 檔案上下文與開啟的分頁
├─ 對話歷史
├─ MCP 工具結構描述
└─ 你輸入的提示

一個 20 字的提示，可能會連同數千個上下文 Token 一起送出。

Coding Agent 乘數效應

一次從 Issue 到 PR 的執行，並不等於一次請求。

Agent 步驟

規劃、搜尋、讀取檔案、編輯、執行測試、檢查失敗、重試。

複利累積

後續步驟會帶著保留的上下文與工具結果。快取與壓縮會影響成本。

實驗 1：Token 剖析

目標

區分可見的提示與隱藏的上下文。

做法：選一個近期的 Copilot 任務。列出可能的上下文來源：開啟的檔案、引用的檔案、指示、歷史、工具、輸出。

討論：哪一個來源最容易控制？

時間：15 分鐘。

第 2.1 部分

提示壓縮

先讓請求清楚，再讓它變短。技術術語與限制條件要保持精確。

一般的精簡語言是預設做法。簡寫為選用。

選用的簡寫

捨棄

沒有增加任務資訊的冗詞與客套話。

保留

技術術語、程式碼、檔名、否定、條件與驗收檢查。

[事物] [動作] [原因]。[下一步]。

當片段式寫法會讓人看不出誰做什麼時，請保留完整句子。

前後對照

冗長精簡
可以請你審查這個 Pull Request，並告訴我是否有任何問題嗎？ 審查 PR。標出問題。
可以解釋這個錯誤訊息是什麼意思，以及我該如何修正嗎？ 說明此錯誤及修正方式。

壓縮層級

層級風格適用時機
精簡散文平實、完整的措辭預設
片段共用術語、簡短子句行為者與條件仍然清楚
高密度簡寫縮寫、箭頭僅在讀者能可靠解讀時

結構化勝過散文

POST /api/users
驗證：
- name: string, 必填
- email: string, 必填, 有效
驗證失敗回傳 400
成功回傳 201，並傳回建立的使用者
儲存至 DB

項目符號與鍵值對讓各自獨立的需求更容易檢查。

以程式碼為中心的提示

自然語言

保留正數、將它們加倍，然後傳回總和。

以程式碼為中心

fn(nums) -> filter(>0) -> map(*2) -> sum

類似 getUserById，但改用 email。找不到時回傳 404。

以不變式表達護欄

冗長的程序壓縮後的不變式
請確保每個 SQL 查詢都將值參數化...SQL：僅使用參數化查詢。禁止串接。
請為任何新程式碼撰寫測試...新程式碼 -> 測試。涵蓋正常 + 錯誤情況。

目標

針對一個真實提示，比較精簡散文、片段與簡寫。

做法：保留檔名、行號、限制條件、完成條件。只刪除贅詞。

比較：哪個版本在不遺失需求的前提下，最容易讓人理解任務？

時間：20 分鐘。

實驗 3：提示 A/B 測試

試試這個與那個

A: 可以看一下 auth 並改善錯誤處理嗎？

B: 檔案：src/auth/login.ts。
錯誤：null 使用者造成 .email 當機。

第 2.2 部分

語言比較

比較 Token 數量，而不是字元數量。

CJK 假設不成立

語言句子Token相較英文
英文I met a huge dog51.0x
西班牙文Conoci a un perro enorme81.6x
中文中文對應句112.2x
日文日文對應句112.2x
俄文俄文對應句142.8x

原因

  • BPE tokenizer 的訓練資料以英文為主。
  • 常見的英文字詞通常只佔一個 Token。
  • CJK 文字的字元較少，但每個字元的 Token 較多。
  • 非拉丁文字通常成本較高；音譯可能有幫助。

實務法則

使用能讓需求清楚的語言。字元較少並不保證 Token 較少。

在這些範例中，英文使用的 Token 較少。在一般化之前，請用目標 tokenizer 測試等效的提示。

實驗 4：Tokenizer 現實檢驗

目標

以實際的 Token 數量來推翻或證實對語言的假設。

做法：選一個提示。翻譯成你最擅長的非英文語言。在 tokenizer 工具中比較 Token 數量。

產出：實測的 Token 數量，以及任何清晰度上的取捨。

時間：20 分鐘。

第 2.3 部分

上下文管理

控制哪些檔案、指示與歷史會被送出。

常駐檔案每一輪都要付費

.github/copilot-instructions.md、AGENTS.md、CLAUDE.md 與類似的檔案可能成為持續存在的上下文。

當兩個檔案都被載入時，重複的規則會讓上下文增加兩次。

先修剪，再壓縮

刪除重複的規則、過時的筆記，以及程式碼中已可見的事實。保留專案特有的陷阱。

可重複使用的回應範本位於「實務設定」。判斷規則是否相關，並不需要估算 Token 數量。

上下文衛生

  • 關閉與目前任務無關的檔案。
  • 讓檔案保持聚焦且小巧。
  • 忽略建構輸出、vendor 目錄、產生的檔案。
  • 在支援的 Business/Enterprise 介面上，對敏感路徑使用 Content Exclusion。
  • 主題改變後，開啟新的對話。

使用限定範圍的指示

---
applyTo: "src/api/**/*.ts"
---
API 慣例：
- 路由放在 src/api/routes/。處理常式保持精簡，邏輯放在 services/。
- 以 zod 驗證。
- 錯誤透過 Result<T,E> 傳回，絕不拋出。

只為相符的檔案載入特定路徑的指引。

常駐 vs 條件式 vs 按需

先正規化豐富格式檔案

對快取友善的行為

持久化圖形導覽

企業注意事項：Content Exclusion

客戶端行動

為敏感檔案、產生的套件組合、大型資料檔案與受法規管制的路徑設定 Content Exclusion。

重要：這是隱私/政策控制，並非一般的 Token 設定。它不適用於 Copilot CLI、雲端 Agent 或 IDE Agent 模式。請檢查目前的官方支援情況。

目標

做法：檢查儲存庫指示、AGENTS/CLAUDE 檔案、開啟的分頁、產生的檔案、MCP 設定。

第 2.4 部分

輸出控制

要求你需要的答案格式。略過不需要的說明。

依任務決定的程式碼輸出

只要程式碼，不要說明。

在團隊已了解變更內容時使用。讓錯誤、缺少的需求與失敗的檢查保持可見。

格式限制

指示適用時機
用一句話回答快速決策或說明
最多 3 個項目符號便於瀏覽的摘要
以 JSON 回覆機器可讀的擷取
是/否，再用一行說明原因審查關卡
只要 Diff修補檔檢查

專案預設值

先給答案。說明的份量與任務相稱，並完整保留驗證證據與阻礙。

使用單一的入門範本，再加入相關的專案規則。

第 2.5 部分

工作流程最佳化

在縮短個別提示之前，先選擇負擔較低的工作流程。

Commit 與 PR 文字很重要

Commit

feat: add password reset via settings page

只有在「為什麼」不明顯時才寫內文。

審查

L42: bug: user 可能為 null。在 .email 前加上防護。

單行、可執行、依嚴重程度編碼。

Ask vs Edit vs Agent

Auto 模型預設值

Auto 是良好的基準：受支援的 Auto 集區、遵循組織政策，依文件所述，符合資格的付費方案 Chat 用量可享折扣。

Auto 並不代表「升級到每個高階模型」。請有意識地固定使用高階模型。

模型變更時重新調校提示

目標模型：GPT-5.5。
指南：<官方提示指南 URL>
檔案：.github/copilot-instructions.md, .github/instructions/*.md
依據指南調整提示。保留行為。減少重工。
只顯示 Diff。

何時不該壓縮

  • 安全警告。
  • 不可逆的操作。
  • 新手引導與教學。
  • 法規/合規用語。
  • 片段會造成歧義的複雜指示。

以使用教練功能形成閉環

第 2.6 部分

常駐上下文問題

更多上下文可能讓 Agent 表現更差，成本也更高。

研究訊號

發現觀察到的影響
由 LLM 產生的上下文檔案在 5/8 的設定中造成損害
平均正確性下降約 2%
Token 成本上升 20-23%
推理負擔在引用的設定中上升約 22%

為什麼上下文會造成傷害

冗餘

重複 Agent 可從程式碼中找到的事實。

注意力

將重要規則埋沒在冗長的上下文中。

錨定

引導 Agent 使用過時的工具。

訊號/雜訊

讓專案特有的陷阱更難被發現。

只保留地雷

保留刪除
使用 uv 而非 pip這是 Python 專案
DB 移轉必須依序執行我們使用 PostgreSQL
不要重構 auth 模組；稽核待處理我們使用 JWT 驗證
部署需要 VPN主要分支受保護

錯誤追蹤器模型

從幾乎空白開始。
Agent 在某處出錯 -> 新增一行。
根本原因修復 -> 刪除該行。

當根本問題修復後，就移除該指示。

實驗 10：地雷修剪

目標

移除不必要的上下文；確認必要的指引仍然保留。

做法：將每條指示標記為可探索、風格、地雷、過時、重複。除了真正的常駐地雷之外，其餘全部刪除或限定範圍。

產出：修剪後的指示草稿，且必要規則完整保留。

時間：35 分鐘。

第 2.7 部分

MCP 與工具成本

已載入的工具定義會增加輸入，即使該工具未被使用。

先量測

/context

System/Tools: MCP + 指示 + 系統提示
Messages: 對話歷史
Free Space: 剩餘上下文

檢查已載入的工具。僅看已安裝的伺服器數量，無法反映延遲載入的定義或快取行為。

每個工具都耗用 Token

元件約略成本
名稱 + 說明20-50 個 Token
簡單的參數結構描述30-80 個 Token
複雜的參數結構描述100-300 個 Token
每個工具合計100-500 個 Token

乘法問題

10 個 MCP 伺服器
x 每個 5 個工具
x 每個工具 200 個 Token
= 每一步 10,000 個 Token

15 個 Agent 步驟 = 150,000 個結構描述 Token

這是假設載入完整目錄的情況，並非實測計費。延遲載入的定義與快取會改變結果。

稽核規則

  • 停用目前不需要的伺服器。
  • 對專案特有的伺服器使用工作區設定。
  • 優先使用內建工具，而非重複的檔案系統 MCP。
  • 偶爾才需要的功能使用技能。
  • 在支援時，依命名空間/模式限定大型外掛程式的範圍。

工具輸出壓縮

RTK

Rust CLI 代理程式會篩選雜訊多的 Shell 輸出：測試、git diff、grep、記錄檔、檔案清單。

rtk init --copilot

snip

可透過 YAML 擴充的命令篩選器，附帶本機節省量統計與團隊維護的規則。

snip init --agent copilot

每個命令路徑只選擇一層輸出篩選器。預設不要同時疊加 RTK 與 snip。

每層一個工具

層工具減少
工作流程回合CodeAct重複的模型-工具迴圈
命令輸出RTK 或 snip冗長的 Shell 結果
命令選擇minimal-context-tools範圍廣泛的搜尋/讀取行為
程式碼庫定位Graphify重複的檔案重讀
可見性Chronicle / Coach你可能忽略的浪費

最大贏家

第 4.2 部分

模型選擇與定價

三種定價檢視

檢視回答的問題
GitHub Copilot 文件方案可用性、模型存取、Auto 行為、已發布的訊號
UBB 架構切換後的 AI 點數預算與治理

Auto：實務意義

  • 從受支援的 Auto 集區中選擇。
  • 受方案與組織政策約束。
  • 在支援的情況下，針對任務最佳化的路由會考量複雜度、健康狀態與可用性。
  • 符合資格的付費方案 Chat 用量可享折扣。
  • 不會自動升級到每個高階模型。

推理強度

強度適用於
低大量的簡單聊天/分類
中在支援時，一般的程式開發與大量使用工具的工作
高/最大架構、安全性、新穎的問題拆解

僅在提供此控制項的模型上使用。

反模式

  • 整天固定使用高階模型。
  • 假設 Auto 可以繞過模型存取政策。
  • 將供應商 API 定價等同於 Copilot 計費。
  • 一開始就為整個組織啟用所有高階模型。
  • 忽略方案/模型的可用性。

日常模型指引

  1. 不確定的日常工作先用 Auto。
  2. 微小且有界限的工作使用輕量模型。
  3. 計畫明確後的一般實作使用中階模型。
