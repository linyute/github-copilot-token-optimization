# 2.6 常駐內容脈絡問題 — 為什麼少即是多

[← 返回指南](index.md)

---

> `AGENTS.md`、`.github/copilot-instructions.md` 與 `CLAUDE.md` 的範圍與工具支援各不相同。一個儲存庫可以使用多個檔案，但每個檔案在其工具載入時都會增加內容脈絡。以下的研究測試的是 `AGENTS.md`。請以它作為修剪其他常駐檔案的參考，而不是將其視為這些格式各自的獨立基準測試。關於壓縮範例，請參閱[第 2.3 部分](04-context-management.md)。

## 2.6.1 研究：內容脈絡檔案往往有害

詳細的內容脈絡檔案是否能提升代理程式的表現？以下的研究檢驗了這個假設。

**蘇黎世聯邦理工學院（ETH Zurich）的研究（Gloaguen 等人，AGENTBENCH，2026 年 2 月）以大規模方式測試了這一點：涵蓋 12 個儲存庫的 138 項任務，使用 4 種不同的程式設計代理程式。** 結果如下：

| 發現 | 資料 |
|---------|------|
| LLM 產生的內容脈絡檔案損害表現 | 在 8 種實驗設定中有 5 種表現下降 |
| 平均正確性變化 | 在 AGENTBENCH 上為 **−2%** |
| 使用 LLM 產生的內容脈絡時的成本增加 | 多消耗 **20-23%** 的 token |
| GPT-5.2 的推理額外負擔 | 有內容脈絡檔案時，推理 token 多出 **22%** |

在這些設定中，產生的內容脈絡檔案增加了成本，卻沒有提升平均正確性。

## 2.6.2 人工撰寫的檔案：頂多是小幅改善

人工撰寫的內容脈絡檔案表現稍好 — 但並不穩定：

| 模型 | 人工撰寫內容脈絡檔案的影響 |
|-------|--------------------------------------|
| 各模型平均 | 約 4% 的改善（不穩定） |
| Claude Code | 使用人工撰寫的內容脈絡反而**更差** |
| 檔案探索率 | 有無內容脈絡檔案都相同 |

檔案探索率沒有改變：即使沒有內容脈絡檔案，代理程式也能找到相關檔案。

## 2.6.3 為什麼更多的內容脈絡反而有害

有四種機制可以解釋這些發現：

**1. 冗餘。** 內容脈絡檔案可能重複 `package.json`、匯入項目與目錄結構中已經可取得的事實。代理程式等於把同樣的資訊處理了兩次。

**2. 注意力。** Liu 等人的〈Lost in the Middle〉（2023）描述了模型對長內容脈絡中間部分資訊的運用較弱。當重要規則被埋在 200 行的 `AGENTS.md` 中時，可能更難被記住。

**3. 錨定。** 代理程式可能過度遵循過時的指引。在 `AGENTS.md` 中提到某個工具，會使其使用率增加 **1.6 倍**，即使另一個工具更適合該任務。

**4. 訊雜比。** 每個內容脈絡 token 都在爭奪模型的注意力。低價值的內容脈絡（例如在 `tsconfig.json` 已存在的情況下，寫「此專案使用 TypeScript」這類例行事實）會稀釋高價值的內容脈絡（例如「不要重構身分驗證模組 — 它有一項待處理的安全性稽核」這類專案專屬的注意事項）。

## 2.6.4 反面觀點：效率與正確性

Lulla 等人（2026 年 1 月）發現，人工撰寫的 `AGENTS.md` **使執行時間減少 29%**，**輸出 token 減少 17%**。他們量測的是效率，而非正確性。

請將這些結果分開看待。更快的導覽很有用，但這並不能證明答案是正確的。

## 2.6.5 內容脈絡檔案中究竟該放什麼

Addy Osmani 的篩選準則（Google，2026）：

> **「代理程式能否透過閱讀你的程式碼自行發現這件事？如果可以，就刪掉它。」**

通過這個篩選的內容：

| 保留 | 刪除 |
|------|--------|
| 「使用 `uv` 而非 `pip`」 | 「這是一個 Python 專案」 |
| 「執行測試時使用 `--no-cache`」 | 「測試位於 `tests/` 目錄」 |
| 「不要重構身分驗證模組」 | 「我們使用 JWT 進行身分驗證」 |
| 「部署需要 VPN 連線」 | 「主要分支受到保護」 |
| 「資料庫移轉必須依序執行」 | 「我們使用 PostgreSQL」 |

請保留專案專屬的陷阱：看起來例行、卻會造成錯誤的事項。請移除代理程式能從程式碼中發現的事實。

## 2.6.6 理想做法：把它當成錯誤追蹤器

```text
從幾乎空白的檔案開始。
代理程式在某處出錯 → 加入一行。
根本原因被修正 → 刪除那一行。
```

當反覆發生的失誤需要時，才加入指引。當根本問題被修正後，就移除該指引。
